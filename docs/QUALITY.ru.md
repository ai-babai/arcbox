# Контракт качества

[English — основной документ](QUALITY.md) · [Участие в проекте](../CONTRIBUTING.md)

Изменение готово после успешного `./scripts/quality.sh` и проверки по ревью-чеклисту. Если проверка падает, изменение возвращается на доработку. Постоянные тесты, генерируемые ими данные, хуки и CI явно разрешены владельцем 07.11.2026.

## Принципы

- **DRY:** поведение архиватора реализуется один раз в ArcboxCore. GUI, CLI и MCP вызывают общий движок. Разбиение, сборка и проверка частей используют общий потоковый подсчёт байтов и SHA-256. Похожий внешний вид ещё не повод создавать общую абстракцию.
- **KISS:** прямые типы Swift, Foundation и нативные элементы macOS. Выделяем реальные обязанности, избегаем бессодержательных обёрток ради метрик.
- **YAGNI:** реализуем текущие сценарии «Открыть / Создать / Распаковать». Настройки, плагины и расширения для гипотетических задач не добавляем.
- **SOLID, прежде всего SRP:** оркестрация архивов, запуск 7-Zip, разбор списка, проверка результата и потоковая работа с частями разделены. Представление и протоколы остаются в адаптерах; движок от них не зависит.

## Что блокирует коммит и слияние

| Проверка | Требование | Инструмент и область |
| --- | --- | --- |
| Форматирование | Без отличий и диагностик | swift-format из Xcode 16.4; Sources, Tests, Package.swift |
| Линт и размер | Без предупреждений; файл ≤500, функция ≤80, тип ≤450 строк | SwiftLint 0.65.1; Sources и Tests; размер тела без пустых строк/комментариев |
| Цикломатическая сложность | Каждая функция/аксессор ≤10 | swift-complexity 1.6.0 на SwiftSyntax; весь production Swift |
| Когнитивная сложность | Каждая функция/аксессор ≤15 | Тот же анализатор |
| CRAP(line) | Среднее <5, максимум ≤30 | Сложность + покрытие исполняемых строк LLVM; ArcboxCore |
| Diff coverage | ≥80% изменённых исполняемых строк | LLVM → Cobertura → diff-cover 9.7.0; ArcboxCore |
| Циклы зависимостей | 0; core не зависит от адаптеров | Граф модулей SwiftPM и компилятор |
| Поведение | Все тесты проходят | XCTest + SwiftCheck: архивы, части, пароли, отмена, пути, лимиты, атомарность |
| Чувствительность тестов | Все мутации заявленной области обнаружены; запуск непустой | Muter 16; ArchivePathPolicy и PartStream; замены сравнений и логических связок |
| Переводы | Одинаковые ключи и printf-параметры | EN/RU, plutil и проверка каталогов |
| Shell-скрипты | Без диагностик и отличий форматирования | ShellCheck 0.11.0 + shfmt 3.14.1 (Bash, 2 пробела, отступы case); scripts/**/*.sh и .githooks/pre-commit |
| Python-инструменты | Линт/формат; McCabe ≤10 | Ruff 0.14.4; весь Python в scripts и Python-тесты |
| Контракт CLI/MCP | JSON, коды выхода, stdin-пароли, части, MCP negotiation/tools | Python unittest через собранный arcbox |
| Надёжность проверок | Все контрактные тесты проходят | Python unittest: формула, области LLVM, пустые данные, ошибки, циклы, совпадение staging с проверенным кодом |

Встроенные подавления линтера/сложности запрещены. Исключений для старого кода нет. Конфигурации инструментов, скрипты и этот контракт меняются согласованно через ревью. Форматтер допускает существующий помощник локализации `L(...)` и соглашение SwiftUI с именованной work-closure и завершающей completion-closure.

## Границы измерений

**CRAP(line)** = `C² × (1 − coverage)³ + C`. Используется покрытие исполняемых строк в диапазоне 0…1, а не покрытие базисных путей или ветвей. Скрипт сопоставляет начало функции из SwiftSyntax с внешней областью функции в LLVM; несопоставленным функциям назначается нулевое покрытие. Полные значения и области доступны в `.build/quality/metrics.json`. Это явно обозначенный вариант метрики, а не заявление об измерении исходного path-based CRAP.

Diff coverage считается от заданной Git-ревизии с учётом staged/working-изменений локально. В PR используется base SHA; для main — ревизия перед push. Если исполняемый core-код не изменялся, знаменателя нет: это не доказательство покрытия UI или протокола.

Покрытие и CRAP пока обязательны для **ArcboxCore**. GUI и CLI/MCP компилируются, проверяются по сложности и размеру, но автоматического порога покрытия для них пока нет. Изменения интерфейса требуют проверки сценариев, размеров панелей, анимаций и Reduce Motion; изменения протоколов — их поведения. Проверка циклов модулей не измеряет все возможные циклы между типами внутри модуля.

SwiftCheck генерирует по 100 примеров на свойство, уменьшает контрпримеры и выводит seed для повторения ошибки. Сохраняйте seed при расследовании. Отдельные примеры проверяют границы и отказные сценарии.

Mutation testing ограничен двумя важными правилами: опасные пути должны отклоняться, потоковая обработка должна соблюдать границы частей. Это **не mutation score всего проекта**. Muter 16 иногда неверно размещает мутации после не-ASCII текста; выбранные файлы чистой политики и потоковой обработки содержат ASCII и проверены на компиляцию с мутациями. Расширяем область вместе с тестами и проверенным обновлением инструмента. Выжившая мутация, тайм-аут, пустой запуск и ошибка компиляции/среды блокируют проверку.

## К самим проверкам применяются те же принципы

`quality.sh` только передаёт аргументы и код выхода в `scripts/quality/gate.py`. В runner выделены понятные этапы: инструменты, исходники, поведение, покрытие/сложность, мутации. Команды запускаются массивами аргументов; ошибка останавливает последующие этапы и даёт ненулевой код выхода.

Python-код вынесен в `.py`, включая настройку/проверку Muter и метаданные релиза: он попадает под Ruff. Shell отвечает за установку инструментов, упаковку и очистку ресурсов процесса. Cleanup регистрируется до подготовки mutation-run, не удаляет чужой lock и убирает свой после ошибки. Старый отчёт о мутациях удаляется до нового запуска. Эти отказы и буквальная передача аргументов проверены поведенческими тестами.

ShellCheck/shfmt проверяют и точку входа, и Git hook. Порог McCabe для Python распространяется на оркестрацию. Область метрик Swift, CRAP и покрытия LLVM остаётся указанной выше; shell-линт не выдаётся за измерение когнитивной сложности или покрытия.

## Как работать

Нужны macOS и **Xcode 16.4 / Swift 6.1.2**, выбранный через Xcode или `DEVELOPER_DIR`. Homebrew нужен разработчику, пользователю готового приложения он не требуется.

```sh
./scripts/setup-quality.sh
xcrun swift-format format --in-place --recursive Sources Tests Package.swift
./scripts/quality.sh --base origin/main
```

Setup устанавливает инструменты, проверенный по SHA-256 анализатор сложности, зависимости из SwiftPM lockfile, diff-cover/Ruff с фиксацией хешей в игнорируемое Python 3.12 окружение и Git hook. Версии проверяются явно; другая версия из Homebrew требует установки согласованной версии либо отдельного изменения политики.

Перед коммитом добавьте все предназначенные изменения в staging. Хук отклоняет незастейдженные изменения и untracked-файлы, чтобы проверенный код совпадал с коммитом; правки файлов или staging во время проверки также блокируют коммит. Несвязанную работу временно убирайте в stash. Запускается **полная проверка, включая мутации**, относительно HEAD; это занимает несколько минут. Исходники автоматически не переписываются. Отчёты и кэши находятся в `.build/`.

Локальный hook можно обойти, поэтому main защищён обязательным `Quality / gate` и требованием PR. GitHub Actions проверяет все PR/push с read-only токеном, без секретов и path-фильтров. Отчёты доступны в artifacts, включая неуспешные запуски.

Для быстрой проверки во время правок: `swift test --enable-code-coverage`, `swiftlint lint --strict`, `./scripts/quality/mutation.sh`. Они не заменяют общий gate перед коммитом. Не используйте `--no-verify`, ослабление порогов, исключение сложных функций или удаление проверок ради зелёного статуса. Ограничение инструмента объясняйте в PR и предлагайте изменение политики на ревью.

## Ревью человеком или агентом

- Как меняется поведение человека/агента и какое требование это закрывает?
- У каждого изменённого модуля одна связная причина изменения?
- Нет ли повторения правил между GUI, CLI, MCP или архивными операциями?
- Достаточно ли самого простого решения для текущей задачи?
- Сохраняются ли оригиналы и атомарность результата? Что происходит при ошибке/отмене?
- Тесты проверяют наблюдаемое поведение и ловят значимые ошибки?
- Ожидание показано правдиво и приятно, с отменой где возможно и поддержкой Reduce Motion?
- Согласованы ли EN/RU, безопасность данных и сценарии «Открыть / Создать / Распаковать»?

Инструменты не могут автоматически подтвердить DRY/KISS/YAGNI/SOLID. Эти вопросы остаются обязательной частью ревью. Ссылки на первоисточники инструментов и метрик — в [английском документе](QUALITY.md#measurement-references).
